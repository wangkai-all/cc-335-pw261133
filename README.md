# 抓取规则灰度控制台

面向持续抓取资料站的规则灰度工具。抓取进程只保存原始页；两个解析进程分别用
旧规则与候选规则处理同一批原始页；入库端只发布一版经过抽样核对的结果。

整个项目只用 Python 标准库，抓取走真实 HTTP，浏览器界面无外部依赖。

## 快速开始

```bash
python3 -m canary.web --port 8000
# 打开 http://127.0.0.1:8000
```

启动后控制台会自动拉起：

| 进程 | 作用 |
| --- | --- |
| 本地资料站（HTTP） | 可改版站点，`/practice-site` 可打开 |
| `canary.crawler` | 抓取、保存原始页、抓取时绑定规则 |
| `canary.worker --rule parse-old` | 旧规则解析进程 |
| `canary.worker --rule parse-new` | 新规则解析进程 |
| `canary.publisher` | 唯一写入已发布库的进程 |

数据默认落在 `var/`（`canary.db` + `raw/<sha>.gz`），可用环境变量覆盖：
`CANARY_VAR`、`CANARY_DB`、`CANARY_RAW_DIR`、`CANARY_SITE_URL`、
`CANARY_SITE_PORT`、`CANARY_CRAWL_INTERVAL`、`CANARY_PARSER_POLL`、
`CANARY_FETCH_TIMEOUT`。

运行测试：

```bash
python3 -m unittest tests.test_pipeline tests.test_console_e2e
```

## 一次完整灰度

1. 控制台初始会抓取资料站并用旧规则发布一批页面。
2. “演示工具”里把资料站切到 `v2`、新增系列 `b`（或直接用右侧灰度面板）。
3. 在“灰度控制”里选范围（例如 30%）开灰度。抓取进程继续跑；抽样范围内的新
   页面版本被分配给新规则，范围外的仍由旧规则发布。
4. “逐字段抽样对照”实时给出四层结论：
   - 覆盖：哪些页面版本两版都有解析结果、切换边界在哪、哪些页面新规则还没处理；
   - 字段覆盖：每个字段在两版里分别有多少页面有值（字段缺失会直接列出）；
   - 字段一致率：两侧都有值时是否一致，描述变长算“扩展”，变短算“截断→字段丢失”；
   - 列表结构：行数、缺键、半空行（拆行）、键集合差异。
5. 结论为 `fail` 时“批准并转正”会被阻止（可人工强制覆盖）；`review` 允许人工
   判断后批准。批准会把暂扣版本全部补齐发布，已发布版本不会重复入库。
6. “回滚到旧规则”把已处理但未发布的新页面用旧规则重新交付，已发布版本保持不变。
7. “模拟解析进程中断”会对灰度解析进程发 `SIGKILL`；页面进度不会丢，恢复进程后
   从已持久化的解析结果续跑。

## 设计要点

### 原始页共享

抓取结果按内容哈希存为 `var/raw/<前两位>/<sha256>.gz`，`page_fetches` 里一行
代表一个“页面版本”。两个解析进程只读这张表和这些文件，互不感知。轮询到相同
内容不会产生新版本；站点回退到更早内容时会成为一次新观察（同一份原始字节仍然
只存一份）。只要字节完全相同，任何规则都可以再次解析，但入库仍受下文闸门约束。

### 各版解析进度

解析进度不存整数游标，而是由 `parsed_documents` 推导：某规则“还缺哪些 fetch”
就是进度，`(fetch_id, rule_id)` 上的唯一约束保证重跑不会重复。`parser_instances`
记录进程身份、心跳和最后处理位置，`parse_attempts` 记录每次尝试（含错误）。
进程被杀后重启会重新计算游标，并从共享原始页继续。每次切换规则边界时写一行
`progress_checkpoints`，作为当时的审计快照。

### 切换边界

`page_fetches.epoch_id` 是抓取发生时的规则纪元，**不可变**，作为审计边界；
真正决定“这份文档能否入库”的是 `publication_assignments`。两者分离使转正/回滚
只需迁移授权，不触碰原始页，也不需要重新抓取：

- 抓取时按页面身份做稳定抽样，决定该版本归灰度还是旧规则；
- 批准时把灰度纪元中所有**尚未发布**的版本迁到转正纪元——包括批准前抓取、
  解析较晚才完成的版本——发布器随后从共享原始页补齐；
- 回滚时把灰度纪元中尚未发布的版本迁到“恢复”纪元（固定旧规则），因此新规则
  已经处理过的页面仍会通过旧规则交付；
- `publish_ledger.version_key` 唯一 + `inventory` 每页一行 + `fetch_id` 只增不减，
  从数据库层面保证同一页面版本不会在两个版本各贡献一次，晚到的旧版本也不会
  覆盖新版本。

## 目录

```
canary/
  site.py          可改版本地站点（真实 HTTP 服务）
  crawler.py       抓取、原始页落盘、抓取时绑定纪元
  rawstore.py      内容寻址原始页存储
  worker.py        单规则解析进程（可中断、可续跑）
  publisher.py     唯一写入已发布库的进程
  state.py         规则纪元状态机与发布闸门
  diff.py          逐字段/列表结构抽样对照
  web.py           HTTP API + 静态界面
  supervisor.py    子进程编排（站点、抓取、两个解析、发布）
  htmltree.py      标准库 HTML 树
  rule_sources.py  旧规则 / 新规则 / 故意不完整的 parse-draft
static/            控制台界面
tests/             流程不变量测试 + 真实 HTTP 端到端测试
```

## 界面能做什么

- 选灰度范围（按页面身份稳定抽样），随时重新抽样；
- 逐字段查看覆盖、一致率、示例，逐页展开旧/新字段与列表行差异；
- 查看切换边界、进度检查点、事件流和发布闸门的拒绝记录；
- 批准转正、回滚、模拟解析进程中断并恢复；
- 改资料站版面、加新系列、改价，制造抓取与解析的真实变化；
- 装入 `parse-draft`（故意在列表页读错价格、截断描述）观察抽样对照如何拦截。

所有数据都是本地生成的，不依赖任何真实账号或外部站点。
